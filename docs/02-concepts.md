# 2 – Concepts and workflow

This document explains *how* the toolkit works and how a database repository that uses it is organised.
The individual scripts are described in documents 4–7.

## 2.1 The problem

A typical DIC operates several linked SQL Server databases – for example an integration database
(`DIZ_NET`) and a staging database (`DIZ_NET_stage`) that reference each other with three-part names.
Tables in selected schemas (here `conf` and `pc`) hold **configuration data** that control the ETL
processes. Without tooling, every change means:

1. writing ALTER scripts by hand,
2. comparing DEV, TEST and PROD manually to find out what is missing where,
3. copying configuration rows between environments,
4. verifying the result – and hoping that nothing was forgotten.

## 2.2 State-based core, migration-based add-ons

There are two classic ways to deploy database changes:

| Approach | Idea | Strength | Weakness |
|---|---|---|---|
| **State-based** (desired state) | The repository contains the *target state* of every object; a tool compares it with a database and generates the change script | Repository is always the complete truth; drift becomes visible; new instances are trivial | Cannot know *intent*: a rename looks like "drop old + create new"; data are not covered |
| **Migration-based** | The repository contains an ordered list of change scripts | Full control over every step, including data | No complete picture of the schema; every step must be written by hand |

DIC-DB-as-Code uses a **state-based core** (SqlPackage + DACPAC) and adds **two migration-based
components** exactly where the state-based approach is weak:

```
                   ┌──────────────────────────┐
  renames/         │ 1. Rename scripts        │  sp_rename BEFORE the comparison
  (migration)      │    db-apply-renames.sh   │  → no drop/create, no data loss
                   └────────────┬─────────────┘
                                ▼
  database/<DB>/   ┌──────────────────────────┐
  (state)          │ 2. Schema comparison     │  SqlPackage: repository vs. target
                   │    db-diff.sh            │  → change script + report + metadata
                   │    db-apply-diff.sh      │  → executed after approval
                   └────────────┬─────────────┘
                                ▼
  data/<DB>/       ┌──────────────────────────┐
  (state per row)  │ 3. Configuration data    │  MERGE per table, one transaction
                   │    db-data-apply.sh      │  → INSERT / UPDATE / DELETE
                   └──────────────────────────┘
```

The order **renames → schema → data** is mandatory: the schema comparison must see the already renamed
objects, and the data scripts need the final table structure.

## 2.3 Building blocks

| Term | Meaning |
|---|---|
| **SQL project** | Folder with one `.sql` file per object (`<Schema>/<ObjectType>/<Object>.sql`) and an SDK-style `.sqlproj`. Built on Linux with `dotnet build`, no Visual Studio needed. |
| **DACPAC** | Compiled model of a database (zip file). Input for SqlPackage. |
| **Publish profile** | XML file that controls how SqlPackage compares and deploys (block on data loss, drop extra objects, …). Two profiles are shipped: conservative for TEST/PROD and permissive for DEV. |
| **Change script** (diff script) | SQLCMD script generated by `db-diff.sh` that brings a *specific* target database to the repository state. Accompanied by a deployment report (XML) and a `.meta` file (target, Git commit, checksums). |
| **Rename script** | Small T-SQL script with `sp_rename`, named after a convention that encodes the database. |
| **Data script** | MERGE script per table with one line per record, generated from a database and editable by hand. |
| **History table** | `dbo.__SchemaDeployHistory` (default) in each target database: which change/rename script ran when, by whom, with which checksum and result. Prevents double execution. |
| **Env file** | Shell file with connection settings for one environment (e.g. `config/test.env`). Never contains passwords. |

## 2.4 End-to-end workflow

```
 once                ┌─────────────────┐
 ──────────────────▶ │ db-extract.sh   │  PROD/reference DB ──▶ database/<DB>/*.sql + .sqlproj
                     └────────┬────────┘                        artifacts/<DB>.dacpac
                              │ db-data-init.sh ──▶ data/<DB>/*.sql (optional)
                              │ git commit
                              ▼
 feature branch      ┌──────────────────────┐
 ──────────────────▶ │ db-provision-dev.sh  │  ──▶ DIZ_NET_DEV_<ticket> (own DEV database)
                     └────────┬─────────────┘
                              │ develop: edit .sql files, rename scripts, data files
                              │ pull/merge request + review (plain text diffs)
                              ▼
 after merge         ┌─────────────┐  ┌──────────────┐  ┌────────────┐  ┌──────────────┐
 (per stage)    ───▶ │ db-build.sh │─▶│ renames      │─▶│ db-diff.sh │─▶│ approval     │
                     │ project →   │  │ (dry run in  │  │ preview    │  │              │
                     │ DACPAC      │  │  preview)    │  │            │  │              │
                     └─────────────┘  └──────────────┘  └────────────┘  └──────┬───────┘
                                                                               ▼
                                     renames → diff → db-apply-diff.sh → db-data-apply.sh
                                     (optionally wrapped in db-backup.sh run)
```

1. **Initial import** – `db-extract.sh` for every database (referenced databases first), optionally
   `db-data-init.sh` for configuration tables. Commit the result.
2. **Development** – each feature branch gets its own DEV database via `db-provision-dev.sh`. Developers
   change `.sql` files (e.g. in VS Code with the *SQL Database Projects* extension, or develop in SSMS and
   update the file) and keep the DEV database current with `--if-exists update`.
3. **Review** – pull/merge request. Table changes, renames and configuration rows appear as normal text
   diffs.
4. **Delivery** – the pipeline builds the DACPAC, shows a preview (change script, report, data dry run)
   and, after approval, runs renames → diff → apply → data on TEST and then PROD.
5. **Operations** – optional drift checks (`db-diff.sh --fail-on-changes`, `db-data-apply.sh --dry-run`)
   detect manual changes in an environment; `db-data-refresh.sh` brings configuration changes made
   directly in a database back into the repository.

## 2.5 Layout of a database repository

The toolkit lives in its own repository (this one) and is embedded into the repository that holds your
database code – preferably as a **Git submodule** so that every database repository pins a known toolkit
version:

```bash
git submodule add https://github.com/Mountainman97/DIC-DB-as-Code.git tools/dic-db-as-code
git submodule update --init        # after cloning the database repository
```

Recommended layout (all paths in this documentation are relative to the repository root):

```
my-dic-databases/
├── tools/dic-db-as-code/         ← this repository (submodule)
│   └── toolkit/scripts/…
├── config/
│   ├── dev.env                   ← connection settings DEV (no passwords)
│   ├── test.env
│   └── prod.env
├── database/
│   ├── DIZ_NET/                  ← SQL project (created by db-extract.sh)
│   │   ├── DIZ_NET.sqlproj
│   │   ├── dbo/Tables/*.sql
│   │   └── <Schema>/<ObjectType>/*.sql
│   └── DIZ_NET_stage/
│       ├── DIZ_NET_stage.sqlproj
│       ├── references/DIZ_NET.dacpac
│       └── …
├── renames/                      ← rename scripts (renameColumn_… / renameTable_…)
├── data/                         ← versioned configuration data
│   └── DIZ_NET/
│       ├── data.conf             ← which tables are versioned
│       └── conf.Parameter.sql    ← one MERGE script per table
├── testdata/                     ← optional post-scripts for DEV databases
├── deploy/diffs/                 ← optional: approved change scripts (audit trail)
├── nuget.config                  ← optional: internal/offline NuGet feed
├── .gitignore                    ← artifacts/, bin/, obj/, *.log, *.local.env
└── <pipeline definition>         ← based on toolkit/examples/pipelines/
```

> **Important:** Change scripts, rename scripts and data scripts must **not** be placed inside an SQL
> project folder. SDK-style projects compile every `*.sql` file below the project folder.
> `db-diff.sh` refuses an `--output-dir` inside the project for this reason.

Shorten the script path in your shell for convenience:

```bash
export PATH="$PWD/tools/dic-db-as-code/toolkit/scripts:$PATH"
db-diff.sh --help
```

## 2.6 Common conventions of all scripts

- `-h` / `--help` shows all options (currently in German).
- **Logs go to STDERR, results to STDOUT** (e.g. the path of a generated script), so scripts can be
  chained: `SCRIPT=$(db-diff.sh …)`.
- **Exit codes:** `0` success, `1` error, `3` "changes found" (only with `--fail-on-changes`).
- Every script stops at the first error (`set -Eeuo pipefail`).
- Settings come from **command-line options > env file (`--env-file`) > environment variables**
  (see [3 – Configuration](03-configuration.md)).
- `DEBUG=1` prints additional details, `NO_COLOR=1` disables coloured output.
- Scripts that change a database support `--dry-run` and ask for confirmation before touching a
  **protected database** unless `--yes` is given.
